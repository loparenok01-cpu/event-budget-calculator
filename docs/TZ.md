# Техническое задание

## «Калькулятор для организатора событий» — MVP

| Поле | Значение |
|---|---|
| Версия | 1.0 |
| Дата | 17.10.2026 |
| Статус | Утверждено |
| Заказчик результата | Организатор событий (бюджет по статьям расходов) |
| Основание | Паспорт проекта `Pasport_proekta.md` |
| Стек | Python + Streamlit + Pandas + Plotly + SQLite |

Документ отвечает на семь главных вопросов: **1) контекст, 2) проблема, 3) аудитория, 4) сценарий, 5) требования, 6) ограничения, 7) приёмка**.

## 1. Контекст — что происходит в бизнесе сегодня

Организатор событий планирует мероприятие с ограниченным лимитом бюджета и фиксированной датой. Расходы раскладываются по статьям: площадка, кейтеринг, декор, ведущий и другие. Подрядчики называют цены заранее — это **план**; оплаты проходят по ходу подготовки — это **факт**.

Как всё устроено сейчас: план и факт разрознены (таблицы, заметки, переписка), единственного места, где бюджет собран по статьям и виден в двух состояниях, нет. Организатор вынужден вести учёт вручную и в нескольких местах одновременно.

## 2. Проблема — что теряем, какой ресурс и по какой причине

| Ресурс | Потеря | Причина |
|---|---|---|
| Деньги | Перерасход обнаруживается постфактум, когда суммы уже потрачены | Нет сопоставления план/факт по статьям и контроля лимита |
| Время | Ручное сравнение вариантов площадки, меню и оформления | Нет единого инструмента учёта |
| Управляемость | Не видно, какая статья «съедает» бюджет | Данные не собраны в одном месте |

Формулировка заказчика (главная история пользователя): **«Как организатор, я хочу видеть план и факт по каждой статье, чтобы заранее заметить перерасход»**.

## 3. Аудитория — кто будет главным пользователем

| Роль | Описание | Доступ в MVP |
|---|---|---|
| **Организатор** — главный пользователь | Создаёт события, ведёт статьи бюджета, следит за перерасходом | Полный: создание, редактирование, просмотр, режим просмотра, экспорт |
| Клиент | Смотрит сводку по событию; оценивает бюджет | Только просмотр: переключатель «Режим просмотра» в интерфейсе (без входа и паролей); получает отчёт файлом (CSV) |

## 4. Сценарий

### 4.1 Главный сценарий

1. Организатор создаёт событие: мероприятие, клиент (необязательно), дата, гости, лимит бюджета.
2. Добавляет статьи: площадка, кейтеринг, декор, ведущий.
3. Вносит плановые и фактические суммы.
4. Смотрит сводку и график по статьям.

### 4.2 Пользовательские истории

| ID | История |
|---|---|
| US-1 | Как организатор, я хочу создать событие с мероприятием, клиентом, датой, числом гостей и лимитом, чтобы бюджет был ограничен заранее |
| US-2 | Как организатор, я хочу добавлять статьи из готовых категорий либо вводить свою через «Другое», чтобы учесть все расходы |
| US-3 | Как организатор, я хочу вносить план и факт с комментарием, чтобы видеть отклонения по каждой статье |
| US-4 | Как организатор, я хочу видеть итог, остаток от лимита и стоимость на гостя, чтобы контролировать бюджет события |
| US-5 | Как организатор, я хочу видеть подсветку перерасхода и график структуры расходов, чтобы быстро находить проблемные статьи |
| US-6 | Как клиент, я хочу смотреть сводку в режиме просмотра и получить отчёт файлом, чтобы оценить бюджет без вмешательства в данные |

### 4.3 Навигация между экранами

- Боковое меню Streamlit: **«Список событий» → «Бюджет события» → «Сводка с графиком»**.
- Кнопка **«Домой»** в боковом меню, доступна на всех экранах: возвращает на главный экран («Список событий») и сбрасывает выбранное событие.
- Выбранное событие хранится в session_state; на «Списке событий» — кнопка «Создать событие» и выбор события из списка.
- Переключатели «Режим просмотра» и «Расчёт на гостя» — в боковом меню, доступны на всех экранах (панель сценария — на экране бюджета); кнопка «Скачать отчёт (CSV)» — на экране сводки.

## 5. Требования

### 5.1 Функциональные требования

| ID | Требование |
|---|---|
| FR-1 | **Список событий.** Отображение всех событий: мероприятие, клиент, дата, гости, лимит, краткий итог (факт, остаток), подпись «версия плана · комментарий» (если заполнены). Действия на карточке: открыть бюджет, изменить, копировать (FR-15), удалить. После создания/копирования событие выбирается автоматически. Переход к бюджету события |
| FR-2 | **Создание события.** Форма: мероприятие (строка, обязательно), клиент (строка, необязательно, ≤ 100 символов), дата (ввод и отображение в формате дд/мм/гггг, BR-6), число гостей (целое ≥ 0), лимит бюджета (сумма > 0, ₽; режим ввода «Всего»/«На гостя» — только способ ввода, в БД хранится итоговый лимит и признак режима); денежные поля формы («Лимит», «Сумма платежа») — текстовые, разряды разделяются неразрывным пробелом (150 000), допускается ввод с обычным пробелом и с запятой как десятичным разделителем; необязательные поля: блок «Оплаты» — список платежей «дата + сумма», до 10 строк (пустая строка — платёж не внесён; заполненный платёж: сумма ≥ 0 и обязательная дата; ничего не внесено — платежей нет; хранение — таблица `payment`, FR-7), «Комментарий» (≤ 200 символов), «Версия плана» (≤ 50 символов, удобно при копиях и пересмотрах), «ID исходного заказа» (≤ 50 символов, при копии подставляется автоматически). Число гостей и лимит — независимые поля: изменение гостей не меняет сохранённый лимит (BR-2, FR-3) |
| FR-3 | **Редактирование и удаление события.** Форма редактирования предзаполняет все поля события; удаление — с подтверждением; статьи удаляются вместе с событием. При режиме лимита «На гостя» — чекбокс «Согласованный пересчёт лимита» (по умолчанию выключен): включён — при сохранении лимит = ставка ₽/гость × новые гости (записывается в БД); выключен — лимит при изменении числа гостей не меняется (BR-2). При изменении числа гостей факт переменных статей (признак «Тарификация на человека») пересчитывается по сохранённой ставке ₽/чел: факт ÷ прежние гости × новые гости; планы, лимит и факт фикс-статей не меняются (BR-2) |
| FR-4 | **Статьи бюджета.** Таблица статей выбранного события: категория, план, факт, комментарий; добавление, редактирование, удаление статьи |
| FR-5 | **Категории.** Выбор из списка: Площадка, Кейтеринг, Декор, Ведущий, Другое. Список категорий отсортирован по алфавиту; поиск — ввод первых букв наименования расхода (список фильтруется по первым буквам, «Другое» остаётся доступным всегда). При выборе «Другое» — поле ввода собственной категории; она сохраняется в общий справочник и доступна при дальнейшей работе (см. BR-1) |
| FR-6 | **План и факт.** Ввод сумм (рубли, ≥ 0, до 2 знаков) и необязательного комментария. В денежных полях «План», «Факт» и тарифов разряды разделяются неразрывным пробелом (150 000); допускается ввод с обычным пробелом и с запятой как десятичным разделителем. Факт обязателен по каждой статье (0 допустим — «не потрачено»). План может быть пустым: пустая ячейка — «не внесено» (NULL) и не приравнивается к нулю; введённый 0 — явный ноль (BR-4); признак «Тарификация на человека» (статья участвует в сценарии FR-16) — чекбокс в форме статьи, по умолчанию выключен, авто-установки по категориям нет; при включённом признаке — два поля-помощника под своими суммами: «Тариф плана, ₽/чел» (сразу под «План») и «Тариф факта, ₽/чел» (сразу под «Факт») (≥ 0, вводятся вручную): при открытии статьи тарифы заполнены по суммам (план ÷ гости и факт ÷ гости; при 0 гостей — пусто), при ручной правке суммы тариф пересчитывается; тариф плана подставляет в «План» сумму = тариф × число гостей события (помощь при первоначальном планировании; согласованный план BR-5 не меняется, итоговое значение «План» можно поправить вручную; при согласованном плане поле «Тариф плана» заблокировано и показывает плановый тариф = план ÷ гости), тариф факта подставляет в «Факт» сумму = тариф × число гостей события (итоговое значение «Факт» можно поправить вручную); в таблице статей под суммами «План» и «Факт» переменной статьи показывается расчётный показатель ₽/чел (сумма ÷ число гостей события; при 0 гостей — «—»; у плана NULL — без показателя) |
| FR-7 | **Сводка.** Шапка бюджета: метрика «Отклонение (Факт − Лимит)» = суммарный факт − лимит — при превышении (> 0) красным с подписью «превышение лимита»; при ≤ 0 — без цвета и подписи (зелёный в шапке не используется; ровно 0 — «0 ₽»). Метрика «На гостя (лимит)» = лимит ÷ число гостей (BR-2): при 0 гостей — «—». Под метрикой «Лимит» — постоянная заметка: «Лимит — договорённость с клиентом, план — расчёт по статьям. Это 2 разных показателя: расхождение допустимо, для наглядности рекомендуется регулировать статьей «Прочие расходы»». Итог плана, итог факта, остаток лимита по плану и по факту = лимит − суммарный план/факт (экран «Сводка с графиком», итоги CSV), стоимость на гостя (план и факт), перерасход и экономия по статьям (с количеством статей «у N из M»). Показатели сгруппированы тремя карточками: «План» (итог, ₽/гость, «Отклонение (План − Лимит)» = суммарный план − лимит: > 0 красным с подписью «план превышает лимит», ≤ 0 без цвета, далее «Отклонение (Факт − План)» = суммарный факт − суммарный план: > 0 красным, < 0 зелёным, при 0 — без цвета), «Факт» (итог, ₽/гость, экономия и перерасход по статьям — порядок «Перерасход», затем «Экономия»; строки выделены мягким фоном, как в образце), «Оплаты» — две колонки «Лимит»/«факт» (макет «Режим Оплаты», образец клиента): «К оплате» = лимит и итог факта; «Внесено итого» = сумма платежей; «Платёж» — по строке на платёж, дата — в колонке «факт»; «Остаток в пределах лимита» = лимит − внесено; «Осталось внести по плану» = итог плана − внесено; «Осталось внести по факту» = итог факта − внесено (колонка «факт»); остатки не уходят в минус (0 + подпись «согласованная переплата +сумма»); мягким фоном выделены строки «Внесено итого» и «Осталось внести по плану» (как в образце); оплата по факту выделена цветом и размером шрифта: «Осталось внести по факту» — красным при сумме > 0, подписи «согласованная переплата +сумма переплаты» и «Полностью оплачено» — зелёным; показатель «Остаток в пределах лимита» — обычным видом, без цветового выделения). Деньги клиента: «Внесено» = сумма платежей со списком «дата + сумма», если > 0. Факт обязателен по всем статьям — расчёты по факту объективны, оговорки о неполноте данных не нужны (BR-4) |
| FR-8 | **Подсветка перерасхода.** По статье (факт > план) — красное отклонение и подпись «Перерасход» в строке; по общему лимиту (остаток < 0) — красная метрика с подписью «превышение лимита»; по правилам BR-3 и BR-4; подсветка и подписи видны и в режиме просмотра |
| FR-9 | **График.** Диаграмма структуры расходов в разрезе категорий (Plotly) по факту и плану; строится строго из того же агрегированного набора данных, что и таблица сводки (NFR-8) |
| FR-10 | **Режим просмотра.** Переключатель в интерфейсе: скрывает формы и кнопки редактирования, оставляет данные, сводку, график и подсветку. Без входа и паролей |
| FR-11 | **Экспорт отчёта клиенту.** Кнопка «Скачать отчёт (CSV)»: шапка события (мероприятие, клиент, дата, гости, лимит), таблица статей, итоги (план/факт, остатки лимита, ₽/гость), блок «Оплаты» (две колонки «Лимит»/«факт»: «К оплате», «Внесено итого», платежи построчно «Платёж» — сумма и дата, «Остаток в пределах лимита», «Осталось внести по плану», «Осталось внести по факту» с подписями состояния), признаки перерасхода. Даты в отчёте — в формате дд/мм/гггг (BR-6). Файл передаётся клиенту |
| FR-12 | **Калькулятор.** Встроенный калькулятор в интерфейсе: базовые арифметические действия (÷ × − + =), ввод с кнопок мышью и командная строка — ввод числа и действий без мыши: Enter разбирает ввод и результат виден сразу, «=» необязателен («12500,50 + 3500» → 16000,5); число может содержать пробелы или запятую («12 500» → 12500, «12,5» → 12.5); команды «C»/«сброс» — очистка, «⌫»/«стереть» — удаление последнего символа; мусорный ввод игнорируется (состояние не меняется). Копирование результата — для подсчёта сумм при планировании; доступен на всех экранах |
| FR-13 | **Согласование плана.** Кнопка «Согласовать план» фиксирует плановые суммы события; пока план согласован, ввод плана по статьям заблокирован (факт, комментарии и категории продолжают редактироваться); снятие блокировки — только явным действием с подтверждением (BR-5) |
| FR-14 | **Поиск событий.** Поле поиска над списком событий: мгновенная фильтрация по названию мероприятия и по клиенту (без учёта регистра, частичное совпадение); счётчик «Найдено: N из M» при активном запросе; пустой результат — «Ничего не найдено» + кнопка «Сбросить поиск», возвращающая полный список; очистка поля тоже возвращает полный список. При создании и копировании события поиск сбрасывается, чтобы новое событие было видно. Влияет только на список, не на данные |
| FR-15 | **Копирование события.** Кнопка копии на карточке списка: имя «… (копия)», клиент, дата, гости, лимит и режим ввода копируются; платежи переносятся из прообраза построчно (уже внесённые деньги сохраняются); комментарий — «копия события «…» от <дата>»; версия плана — следующая (vN → v(N+1) от текущей даты; дата в формате дд/мм/гггг, BR-6; при отсутствии формата — v1 от текущей даты); «ID исходного заказа» — исходный ID события-прообраза (или уже заполненный ID); согласование плана не переносится (BR-5). Статьи копируются: категория, план, комментарий, признак «Тарификация на человека»; факт = 0 (BR-4). Выбор переключается на копию. **Привязка:** копия связана с прообразом полем `parent_id` (FK на event, ON DELETE SET NULL); при удалении прообраза копии сохраняются, привязка очищается; копия от копии привязывается к своей копии (цепочка сохраняется). В карточке копии — подпись «Копия события «…» (ID N)» и кнопка «Открыть прообраз»; в карточке прообраза — «Создана копия: ID …» и кнопка «Открыть копию» (самая свежая). **Цепочка переходов (Копия → Прообраз → Копия):** в бюджете копии — кнопка «Перейти к прообразу» (запоминает переход), в бюджете и на экране сводки прообраза — кнопка «← Вернуться в копию», показываемая после прихода из копии; переход «Открыть прообраз» из списка тоже запоминает возврат. Все эти кнопки видны и в режиме просмотра (FR-10) |
| FR-16 | **Расчёт на гостя (сценарий).** Переключатель в боковом меню (по аналогии с FR-10, независим от режима просмотра). Панель сценария на экране бюджета: число гостей N (целое ≥ 0, по умолчанию — текущие гости), база фикс-статей «Факт/План» (по умолчанию «Факт»), для каждой статьи с признаком «Тарификация на человека» — поле «Тариф, ₽/чел» (≥ 0, до 2 знаков; разряды разделяются неразрывным пробелом; подсказка — текущий ₽/гость статьи; по умолчанию пусто). Расчёт: переменные статьи = тариф × N; фикс-статьи = значение из бюджета по базе (план NULL — «не внесено», в итог не входит); итог = сумма. Показываются: итог расчёта, ₽/гость сценария (N = 0 → «—», BR-2), отклонение от лимита и от текущего итога базы — эти показатели вынесены в рамку выделения; в таблице статей — колонка «Расчёт» с заголовком и значениями, выделенными цветом и полужирным (меняющиеся цифры заметны клиенту, в том числе в режиме просмотра FR-10). Режим ничего не изменяет в событии: лимит, планы и гости остаются прежними, выключение возвращает обычный вид; перенос результата — вручную (редактирование события/статей). Доступен и в режиме просмотра (FR-10) |

### 5.2 Бизнес-правила

#### BR-1. Категории

- Базовые категории — фиксированный список: **Площадка, Кейтеринг, Декор, Ведущий**. Всегда присутствуют в выпадающем списке, удаление и переименование невозможны.
- Пункт **«Другое»**: организатор вводит название собственной категории (например, «Фотограф», «Транспорт»). Категория сохраняется в общий справочник и затем доступна при работе с любыми событиями.
- Каждая статья принадлежит ровно одной категории; пустая категория запрещена.
- Удаление пользовательских категорий в MVP не предусмотрено (см. раздел 6).

#### BR-2. Расчёт на гостя

- Стоимость на гостя (план) = итог плана ÷ число гостей.
- Стоимость на гостя (факт) = итог факта ÷ число гостей.
- Округление — до 0,01 ₽.
- Если число гостей = 0 — значение не рассчитывается, отображается «—» с подсказкой «укажите число гостей».
- Число гостей — целое ≥ 0 (0 допустим: событие ещё готовится).
- Факт обязателен по каждой статье (BR-4): стоимость на гостя (факт) всегда считается по полному факту, без оговорок о неполноте данных.
- **Изменение числа гостей:** лимит события и планы по статьям не пересчитываются автоматически (молчаливый пересчёт исключён); ₽/гость (план и факт) пересчитываются по новому числу гостей сразу. Если после изменения гостей суммарный план превышает лимит — срабатывает сигнал BR-3 «План превышает лимит» (самостоятельная корректировка плана — решение организатора). Согласованный пересчёт лимита — только явным чекбоксом «Согласованный пересчёт лимита» в форме редактирования (FR-3): ставка ₽/гость × новые гости; без чекбокса лимит остаётся прежним.
- **Пересчёт факта переменных статей (исключение из правила выше):** при изменении числа гостей факт статей с признаком «Тарификация на человека» пересчитывается автоматически — при сохранении формы события (FR-3). Ставка ₽/чел сохраняется: новый факт = факт ÷ прежние гости × новые гости (округление до 0,01 ₽). Планы, лимит события и факт фикс-статей не меняются; согласованный план остаётся защищённым (BR-5). Если гостей не было (0) или их не стало (0) — пересчёт не выполняется, факт сохраняется, организатор видит уведомление о пропуске.
- Сценарный пересчёт (режим «Расчёт на гостя», FR-16) — только показ варианта: событие, лимит и статьи не изменяются; перенос результата — вручную.

#### BR-3. Правило перерасхода

- **По статье:** перерасход, если внесён план и `факт > план`. Отклонение = факт − план (в ₽, со знаком). Введённый 0 участвует в сравнении как обычное значение.
- Статья с обязательным фактом и пустым планом — пометка «Статья без плана» (расход вне плана; не «перерасход» и не «экономия»), отклонение не считается.
- **По лимиту события:** остаток = лимит − суммарный факт. Перерасход лимита — если остаток < 0; величина превышения показывается сразу (деньги уже потрачены сверх лимита).
- **Подсветка:** строка статьи с перерасходом выделяется красным и подписана «Перерасход»; метрика остатка/лимита — красным; в режиме просмотра подсветка и подписи сохраняются.
- Дополнительное предупреждение: если суммарный план > лимит — сообщение «План превышает лимит» (не ошибка, сигнал «заранее заметить перерасход»).
- Положительный остаток подписывается как «Экономия»: факт полный по правилу BR-4, оговорки о неполноте данных не требуются.

#### BR-4. Пустой план и обязательный факт

- **Факт обязателен** по каждой статье: сохранить статью без факта нельзя; допустимо только число ≥ 0. Введённый 0 — явный ноль («не потрачено»), участвует в расчётах как обычное значение.
- План может быть пустым: пустая ячейка хранится как NULL («не внесено») и не приравнивается к нулю в расчётах и подписях итогов.
- Факт всегда полон → остаток по факту (лимит − суммарный факт) объективно отражает ситуацию; «ложная экономия» исключена по построению.
- Перерасход лимита показывается сразу при превышении суммарным фактом.
- Сводка, таблица статей и график обязаны отображать один и тот же агрегированный набор данных (NFR-8); расхождение между ними считается дефектом.

#### BR-5. Защита согласованного плана

- Событие имеет признак «План согласован» (по умолчанию — не согласован). План считается согласованным только после явного действия организатора (кнопка «Согласовать план»).
- **Пока план согласован:** поле «План» в формах добавления и редактирования статей заблокировано — случайное исправление плановой суммы исключено. У переменной статьи (FR-6) вместе с планом блокируется и поле «Тариф плана, ₽/чел»: оно показывает плановый тариф = плановая сумма ÷ число гостей события (при 0 гостей или пустом плане — пусто). Факт, тариф факта, комментарии и категории остаются доступными; вновь добавляемые статьи сохраняются с пустым планом (NULL, BR-4).
- **Снятие блокировки** («Разблокировать план») — только явным действием с подтверждением; без подтверждения блокировка не снимается.
- Блокировка — защита от случайного исправления, а не права доступа: организатор всегда может разблокировать план осознанно.
- После разблокировки план редактируется в обычном порядке (≥ 0 или пусто).

#### BR-6. Формат даты

- Даты везде в интерфейсе (поля ввода, подписи на карточках, сводка) и в экспорте CSV отображаются в формате **дд/мм/гггг** (например, 14/11/2026).
- Поле выбора даты использует маску дд/мм/гггг.
- В БД дата хранится в ISO-формате «ГГГГ-ММ-ДД» — формат хранения не зависит от формата отображения.
- Дата платежа — тот же формат и те же правила.

1. **Список событий** — таблица/карточки событий (мероприятие, клиент, дата, гости, лимит, факт, остаток, подпись «версия плана · комментарий»); действия карточки: открыть бюджет, изменить, копировать, удалить; поле поиска по мероприятию и клиенту со счётчиком и кнопкой «Сбросить поиск» (FR-14); форма/кнопка «Создать событие» (мероприятие, клиент, дата, гости, лимит с режимом ввода, платежи «дата + сумма» до 10 строк, комментарий, версия плана, ID исходного заказа); редактирование события: те же поля + чекбокс «Согласованный пересчёт лимита» при режиме «На гостя» (FR-3); при смене числа гостей — пересчёт факта переменных статей по ставке ₽/чел (BR-2).
2. **Бюджет события** — шапка с данными события (ID, мероприятие, клиент, дата, гости, версия плана, комментарий, ID исходного заказа; лимит с подметкой «Лимит — договорённость… 2 разных показателя», метрика «На гостя (лимит)» = лимит ÷ гости (при 0 гостей — «—»), метрика «Отклонение (Факт − Лимит)» — красным только при превышении; деньги клиента — в группе «Оплаты»); таблица статей (категория, план, факт, отклонение, пометки «Статья без плана»/«Перерасход», комментарий; у переменных статей под суммами «План» и «Факт» — расчётный ₽/чел = сумма ÷ гости); при включённом переключателе «Расчёт на гостя» — панель сценария над таблицей (число гостей, база «Факт/План», тарифы переменных статей; показатели «итог расчёта», «₽/гость» и отклонения — в рамке выделения) и колонка «Расчёт» в таблице статей с выделенными значениями (FR-16); форма добавления статьи с выбором категории — список по алфавиту с поиском по первым буквам наименования (включая «Другое»); кнопки «Согласовать план»/«Разблокировать план» (BR-5); панель сводки тремя группами: «План» (итог, ₽/гость, «Отклонение (План − Лимит)» — красным с подписью при превышении, далее «Отклонение (Факт − План)» — красным при перерасходе, зелёным при экономии), «Факт» (итог, ₽/гость, экономия и перерасход по статьям — порядок «Перерасход», затем «Экономия»; строки выделены мягким фоном, как в образце), «Оплаты» (две колонки «Лимит»/«факт»: «К оплате», «Внесено итого» с платежами построчно «Платёж» — дата в колонке «факт», «Остаток в пределах лимита», «Осталось внести по плану», «Осталось внести по факту» с подписями состояния; мягким фоном выделены «Внесено итого» и «Осталось внести по плану»); кнопка «Изменить событие»; кнопка перехода к сводке.
3. **Сводка с графиком** — метрики (итог плана, итог факта, остатки лимита по плану и факту, стоимость на гостя, перерасход по статьям, статус лимита, «Внесено клиентом», «Остаток в пределах лимита» и «Осталось внести по факту» с подписями состояния), график структуры расходов по категориям (Plotly), кнопка «Скачать отчёт (CSV)».
4. **Калькулятор** — виджет в боковом меню (экспандер «Калькулятор», FR-12), доступен на всех трёх экранах: кнопки мышью и командная строка (ввод числа и действий с клавиатуры), копирование результата.

### 5.5 Технологии, среда и порядок запуска

- Python 3.x; Streamlit — интерфейс; Pandas — таблицы и расчёты; Plotly — график; SQLite (модуль `sqlite3`, входит в Python) — хранилище (как в уроке OCu03).
- Зависимости фиксируются в `requirements.txt` (streamlit, pandas, plotly, pytest).
- Слои разделены: `db.py` — доступ к данным (SQLite); `calc.py` — чистые функции расчётов (итоги, отклонения, ₽/гость, покрытие, правила BR-2…BR-4) без импорта Streamlit; `app.py` — только интерфейс, вызывающий `calc.py`. Пересчёты в `app.py` запрещены.
- Хранилище — один файл базы данных в каталоге проекта.

**Порядок запуска (Windows, из папки проекта):**

```bat
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
streamlit run app.py
```

- Приложение открывается на http://localhost:8501; консоль занята — это нормально, остановка — Ctrl+C.
- Если порт 8501 занят: `streamlit run app.py --server.port 8511` → http://localhost:8511.
- Проверка работоспособности: http://localhost:8501/_stcore/health должен отвечать `ok`.
- Локальное выполнение, доступ в интернет не требуется.

| NFR-9 | **Визуальный стиль.** Спокойная палитра (кремовый фон, мятный второй фон, золото основного действия); крупная обложка на экране списка; единые карточки и радиусы; заметное главное действие («Создать событие»); ограниченная ширина текста; состояния наведения и фокуса; короткие спокойные анимации; строки статей бюджета — карточки в цвет кнопок; показатели «На гостя (план)» и «На гостя (факт)» — увеличенным шрифтом; увеличенный базовый размер интерфейса (тема `baseFontSize = 18` — пропорциональный масштаб текста и элементов); заголовки — системный serif; контраст подписей на кремовом фоне; текущая строка (открытое событие в списке, редактируемая статья) выделена; плавное появление блоков при переключении экранов и строк; адаптивность таблицы статей: при ширине контейнера ≤ 820px шапка таблицы скрывается, подпись значения переезжает в ячейку («План: 70 000 ₽»), строка представляется карточкой с категорией-заголовком и парами значений (План/Факт, Отклонение/Комментарий), кнопки действий — на всю ширину; внешние библиотеки, шрифты, изображения и API не используются (только CSS в `app.py`, тема в `.streamlit/config.toml` и системные шрифты) |

## 6. Ограничения MVP

Что сознательно исключается и почему:

| № | Исключено | Почему |
|---|---|---|
| 1 | Авторизация, пароли, роли | Режим просмотра — переключатель в интерфейсе (согласовано с заказчиком) |
| 2 | Облако, синхронизация, работа нескольких пользователей | Локальный однопользовательский инструмент |
| 3 | Сравнение альтернативных смет (несколько площадок, меню, оформления) | Задача заявлена в проблеме, но результат MVP — план/факт одного события; сравнение вариантов — следующая итерация |
| 4 | График платежей по датам, напоминания, календарь | Не влияет на главный сценарий и приёмку |
| 5 | Интеграции (почта, мессенджеры, кассы), экспорт в PDF | Отчёт передаётся клиенту файлом CSV |
| 6 | Удаление и переименование пользовательских категорий | Упрощение справочника для MVP |
| 7 | Версии смет, сценарии «что если», сводная аналитика между событиями | Не нужны для заявленного результата |
| 8 | Молчаливый (автоматический) пересчёт лимита при изменении числа гостей | Лимит — договорённость с клиентом в абсолютной сумме; без явного действия он не меняется. Согласованный пересчёт — только чекбоксом в форме (FR-3, BR-2); сценарный расчёт «а если гостей N» — режим «Расчёт на гостя» (FR-16), данные не изменяет. Автоматически пересчитывается только факт переменных статей — по сохранённой ставке ₽/чел (BR-2); планы и лимит остаются как есть |

## 7. Приёмка

**Образ результата, который описал заказчик:** бюджет по статьям расходов — план и факт по каждой статье, видимый перерасход, сводка с графиком.

**Критерии приёмки:**

- [ ] **7.1** Категории, расчёт на гостя и правило перерасхода реализованы по BR-1…BR-5
- [ ] **7.2** Список событий работает; событие создаётся с мероприятием, клиентом (необязательно), датой, гостями и лимитом (включая необязательные поля: платежи «дата + сумма» до 10 строк, комментарий, версия плана, ID исходного заказа); редактирование предзаполняет форму; копирование даёт копию с планом статей и фактом 0 и привязкой к прообразу (кнопки «Открыть прообраз»/«Открыть копию», копии переживают удаление прообраза) (FR-1…FR-3, FR-15); при смене числа гостей лимит не меняется без чекбокса «Согласованный пересчёт лимита», с ним — лимит = ставка × новые гости (FR-3, BR-2); факт переменных статей пересчитывается по сохранённой ставке ₽/чел, планы и лимит не меняются (FR-3, BR-2); клиент виден в карточке и сводке
- [ ] **7.3** Статьи бюджета добавляются с категорией, планом, фактом и комментарием; «Другое» позволяет ввести собственную категорию; признак «Тарификация на человека» ставится вручную и по умолчанию выключен (FR-4…FR-6)
- [ ] **7.4** Сводка показывает итог плана и факта, метрику «Отклонение (Факт − Лимит)» (красный только при превышении) и метрику «На гостя (лимит)» = лимит ÷ гости («—» при 0 гостей) в шапке, «Отклонение (План − Лимит)» и «Отклонение (Факт − План)» в группе «План» (в таком порядке), остатки лимита по плану и факту (экран «Сводка с графиком»), стоимость на гостя, «Остаток в пределах лимита», «Осталось внести по плану» и «Осталось внести по факту» с учётом денег клиента; факт обязателен по каждой статье (FR-7, BR-4)
- [ ] **7.5** Перерасход подсвечен по статье (красное отклонение и подпись «Перерасход») и по общему лимиту; статьи без плана подписаны; подсветка и подписи сохраняются в режиме просмотра (FR-8, BR-3, BR-4)
- [ ] **7.6** График структуры расходов построен и совпадает с данными таблицы сводки (FR-9)
- [ ] **7.7** Режим просмотра переключается и скрывает редактирование; отчёт CSV скачивается, содержит итоги, покрытие и признаки перерасхода (FR-10, FR-11)
- [ ] **7.8** Расчёты отделены от интерфейса (`calc.py`), есть автоматические тесты (NFR-7); сводка, таблица и график построены по одним данным (NFR-8)
- [ ] **7.9** После «Согласовать план» поле плана заблокировано, факт редактируется; разблокировка — только с подтверждением (FR-13, BR-5)
- [ ] **7.10** Калькулятор доступен на всех экранах: считает кнопками мышью, принимает командную строку (ввод с клавиатуры, «=» необязателен), копирует результат (FR-12)
- [ ] **7.11** Поиск по мероприятию и клиенту фильтрует список, счётчик показывает «Найдено: N из M», пустой результат подписан и сбрасывается кнопкой «Сбросить поиск»; после создания/копирования поиск очищен и новое событие видно (FR-14)
- [ ] **7.12** Приложение протестировано, опубликовано, оформлен кейс
- [ ] **7.13** Режим «Расчёт на гостя» показывает вариант при другом числе гостей (переменные статьи × тариф, фикс-статьи по базе «Факт/План»), итог, ₽/гость и отклонения — показатели панели в рамке выделения; в таблице колонка «Расчёт» с выделенными значениями; ничего не изменяет в событии, выключение возвращает обычный вид (FR-16)

**Порядок проверки:**

1. Пройти главный сценарий (п. 4.1) на чистой базе данных: создать событие → добавить 4 статьи → внести план и факт → открыть сводку.
2. Граничные случаи: лимит 0 (отказ валидации), 0 гостей («—»), факт при нулевом плане («Статья без плана»), превышение лимита (красный остаток), выбор «Другое» → повторный выбор сохранённой категории, смена гостей без чекбокса «Согласованный пересчёт лимита» (лимит прежний) и с чекбоксом (лимит = ставка × гости).

5. Переключить «Режим просмотра»: редактирование скрыто, подсветка видна, отчёт скачивается.
6. Согласовать план: поле плана статьи заблокировано, факт и комментарии правятся; «Разблокировать план» — только с подтверждением.
7. Сверить чек-лист 7.1–7.12; при совпадении — результат принят.
