## 1. Назначение проекта

**Цель:** Помочь организатору собрать бюджет события по статьям, сравнить план и факт и сразу увидеть перерасход.

**Ожидаемый результат (продукт):** работающее веб-приложение MVP, которое выдаёт заказчику — **бюджет по статьям расходов** с сопоставлением план/факт, стоимостью на гостя и визуально подсвеченным перерасходом.

## 2. Контекст и проблема

**Как устроено сегодня.** Организатор планирует событие (дата, гости, лимит бюджета) и раскладывает расходы по статьям: площадка, кейтеринг, декор, ведущий. Плановые суммы фиксируются заранее, фактические — по мере оплаты подрядчикам. Сейчас план и факт живут в разрозненных таблицах, заметках и переписке.

**Проблема.** Клиенту сложно сравнивать варианты площадки, меню и оформления; перерасход обнаруживается постфактум, когда деньги уже потрачены.

**Что теряем.** Деньги (уход за лимит) и время (ручное сопоставление плана и факта по статьям).

**Главная история пользователя:** «Как организатор, я хочу видеть план и факт по каждой статье, чтобы заранее заметить перерасход».

## 3. Пользователи и роли

| Роль | Кто | Доступ в MVP |
|---|---|---|
| Организатор | Владелец события, главный пользователь | Полный: создание и редактирование событий, статей, категорий |
| Клиент | Заказчик события | Только просмотр: переключатель «Режим просмотра» в интерфейсе (без входа и паролей); получает отчёт файлом (CSV) для оценки бюджета |

## 4. Границы MVP

### Входит в MVP

- Список событий с поиском по мероприятию и создание события (мероприятие, клиент — необязательно, дата, гости, лимит бюджета)
- Статьи бюджета: категория, план, факт, комментарий
- Категории: фиксированный список (Площадка, Кейтеринг, Декор, Ведущий) + «Другое» — пользователь вводит собственные категории
- Сводка: итог по плану и факту, остатки лимита (по плану и по факту), стоимость на гостя, перерасход по статьям
- Подсветка перерасхода по статье и по общему лимиту
- Защита согласованного плана: после «Согласовать план» поля плана блокируются (факт и комментарии правятся), разблокировка — с подтверждением
- Встроенный калькулятор для подсчёта сумм при планировании
- График структуры расходов (Plotly)
- Режим просмотра для клиента и экспорт отчёта (CSV) для передачи клиенту
- Локальное хранение данных в SQLite

### Вне MVP (и почему)

| Исключено | Причина |
|---|---|
| Авторизация, пароли, роли | Режим просмотра реализуется переключателем в интерфейсе |
| Облако, синхронизация, несколько пользователей одновременно | Локальный однопользовательский инструмент |
| Сравнение альтернативных смет (несколько площадок/меню) | Результат MVP — план/факт одного события; сравнение вариантов — следующая итерация |
| График платежей по датам, напоминания, календарь | Не влияет на главный сценарий и приёмку |
| Интеграции (почта, мессенджеры, кассы), экспорт в PDF | Отчёт передаётся клиенту файлом CSV |
| Версии смет, сценарии «что если», аналитика между событиями | Не нужны для заявленного результата |

## 5. Ключевые бизнес-правила

Полные формулировки — в TZ.md, раздел 5.2.

1. **Категории.** Статья относится ровно к одной категории. Базовые: Площадка, Кейтеринг, Декор, Ведущий. Пункт «Другое» позволяет ввести собственную категорию, которая сохраняется в общий справочник и доступна при дальнейшей работе.
2. **Расчёт на гостя.** Стоимость на гостя = итоговая сумма ÷ число гостей (₽/гость, план и факт отдельно), округление до 0,01 ₽; при нуле гостей — значение «—».
3. **Правило перерасхода.** Статья: перерасход, если факт > план. Событие: перерасход лимита, если суммарный факт > лимит (остаток < 0). Оба случая подсвечиваются; подсветка сохраняется в режиме просмотра.
4. **Пустые значения.** План может быть пустым («не внесено», не ноль); факт обязателен по каждой статье (≥ 0, включая 0 «не потрачено») — остаток лимита по факту объективен, «ложная экономия» исключена по построению.
5. **Защита согласованного плана.** План фиксируется действием «Согласовать план»; после этого плановые суммы заблокированы от случайных исправлений, факт продолжает вноситься; разблокировка — только с подтверждением (TZ.md, BR-5).

## 6. Критерии успеха (образ результата)

MVP считается принятым, если заказчик подтверждает:

- [ ] категории, расчёт на гостя и правило перерасхода описаны и работают
- [ ] есть список событий и создание события (мероприятие, клиент, дата, гости, лимит); поиск по мероприятию фильтрует список
- [ ] статьи бюджета вносятся с планом и фактом по категориям
- [ ] сводка показывает итог плана/факта, остатки лимита (по плану и по факту), стоимость на гостя; факт обязателен по каждой статье
- [ ] перерасход подсвечен по статье и по общему лимиту; статьи без плана и без факта подписаны
- [ ] после согласования план заблокирован от случайных изменений, факт редактируется; разблокировка с подтверждением
- [ ] калькулятор доступен на экране и считает
- [ ] построен график структуры расходов на тех же данных, что и таблица сводки
- [ ] расчёты отделены от интерфейса и покрыты автотестами
- [ ] режим просмотра работает, отчёт передаётся клиенту
- [ ] приложение протестировано, опубликовано, оформлен кейс

## 8. Риски и допущения

**Риски**

| Риск | Меры |
|---|---|
| Двойное трактование «перерасхода» (по статье / по лимиту) | Правила зафиксированы в TZ.md, п. 5.2 (BR-3) |
| Ошибки ввода сумм и дат | Валидация ввода, сообщения на русском (NFR-3) |
| Слишком широкая трактовка MVP (сравнение вариантов и т.п.) | Границы зафиксированы в разделе 4 |
| Нехватка времени практики | Этапность работ по разделу 7; приёмка — чек-лист TZ.md |
| Расхождение графика и таблицы; неотделимые от интерфейса расчёты; пропуск обязательного факта | BR-4, NFR-7 (модуль calc.py с автотестами), NFR-8 (единый источник данных), NFR-3 (валидация) — TZ.md |

**Допущения**

- Один организатор работает локально; данные хранятся в одном файле SQLite.
- Суммы — рубли с точностью до 0,01; лимит события — строго больше 0; число гостей — целое ≥ 0.
- Резервное копирование — копирование файла базы данных вручную.
- Сроки этапов определяются расписанием практики.
